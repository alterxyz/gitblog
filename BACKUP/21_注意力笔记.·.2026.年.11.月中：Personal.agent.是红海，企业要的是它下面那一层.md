# [注意力笔记 · 2026 年 11 月中：Personal agent 是红海，企业要的是它下面那一层](https://github.com/alterxyz/gitblog/issues/21)

> 注意力笔记：我最近把注意力放在哪，以及我怎么看。

这一期原本是我给一次技术讨论准备的关注点清单，这里是扩写后的公开版。资料截至 2026-11-16，文中日期都是 2026 年。事实尽量附出处；标「我的看法」的是我个人的判断，欢迎拍砖。

我在 Dify 做产品，文中的「我们」指 Dify。但这里写的都是我个人的看法，不是公司的计划或承诺。

## 一、一句话

Personal agent 是红海。但它下面那一层，也就是「长时、常驻、可调度的 agent」，企业比个人更需要：企业有 7×24 小时的业务，有降本增效的压力，有调度，有审计。

所以我的主张是：不跟 Codex、Claude Code、WorkBuddy 这些桌面 agent 抢入口，而是给它们提供企业里的运行环境、权限和记录，共享它们的增长红利。协作，不竞争。

## 二、Agent 的运行底座：要替代的不是 K8s，是「一个 agent 一个常驻 Pod」

**事实**

- **Agent Substrate**（[仓库](https://github.com/agent-substrate/substrate)）：Google 发起，19 名维护者里 16 名来自 Google、3 名来自 Solo.io（[维护者名单](https://github.com/agent-substrate/substrate/blob/main/MAINTAINERS.md)），Apache-2.0，Go 写的。它把大量有状态的 agent 会话映射到少量预热的 worker 上；会话空闲时把内存和文件快照出去，请求来时自称 500 毫秒内恢复。每个会话跑在 gVisor 或 microVM 里，不支持普通容器；每个会话有独立身份，凭据由出口网关注入、不进沙箱。11-05 发 1.0、捐入 CNCF Sandbox，同日在 GKE 上 GA（[Google 博客](https://cloud.google.com/blog/products/containers-kubernetes/open-infrastructure-for-autonomous-agents-comes-to-cncf)）。**README 自称跑在标准 K8s 之上**，不是 K8s 的替代品。
- 它的成熟度：11 月中旬约 6800 star，项目自述「很年轻」。Google 说 Nous Research 是设计伙伴；Solo.io 的 kagent 1.0（11-10）整个跑在它上面（[Solo.io](https://www.solo.io/blog/announcing-kagent-1-0-ga)）。独立的生产规模数据我没查到，「10 倍密度」是官方口径。文档自己写了一条风险：异步挂起时如果节点先挂了，状态可能丢。
- **Gemini API Managed Agents 的自托管环境**（[官方指南](https://github.com/google-gemini/gemini-api-cli/tree/main/docs/self-hosted)，11-10 加进官方 CLI 仓库；Managed Agents 本身还是预览）：
  - 分工：Google 继续管编排，agent 的内置工具（执行 shell、读写和编辑文件、列目录、搜索）跑在你自己的机器里。连接全是出站 HTTPS，不用开入站端口。
  - 两种跑法：一个 worker 直接连上去；或者拆成两半，持有密钥的轮询器放在你信任的控制面，真正执行代码的沙箱里一个 API 密钥都没有，只拿一次交互有效的短期租约令牌。
  - 执行环境：官方给了 Docker、Podman、Cloud Run、Vercel Sandbox、Daytona、E2B、Modal、Fly.io、Cloudflare 的接法。K8s 方案只列了 Agent Substrate 一家，还附了完整的 Go 集成代码（[ate-gemini](https://github.com/google-gemini/gemini-api-cli/tree/main/docs/self-hosted/agent-substrate)）：每个环境对应一个 Substrate actor，跑在 gVisor 里，空闲 1 分钟（默认值）就挂起，出站流量默认拒绝。安全建议里也写明，不可信的负载要放进容器、Agent Substrate 或 microVM。另有报道说 Gemini Managed Agents 自己就跑在 Substrate 上（[SiliconANGLE](https://siliconangle.com/2026/11/11/agent-sandboxing-how-google-s-substrate-isolates-ai-agents-kubeconna/)，二手）。
  - 一条醒目的警告：这套集成不认证交互背后的用户，谁拿到项目的 API key，谁就能在你的 actor 里跑代码。多用户、多租户的认证和权限，要你自己的服务在调 Gemini 之前做掉。
- **Vercel Fluid Compute**：一个函数实例并发处理多个请求，CPU 只在代码执行时计费，等 LLM 返回的时间不收 CPU 钱（[2025-06 起](https://vercel.com/blog/introducing-active-cpu-pricing-for-fluid-compute)）。单次调用最长 800 秒（beta 可到 30 分钟，[限制说明](https://vercel.com/docs/functions/limitations)）；更长的任务要配它的 [Workflow SDK](https://vercel.com/blog/workflow-sdk-5)（v5，11-12 发布）和 [Sandbox](https://vercel.com/blog/vercel-sandbox-is-now-generally-available)。它解决的是计费，不是长时有状态。
- **同类**：K8s 官方子项目 [agent-sandbox](https://kubernetes.io/blog/2026/03/20/running-agents-on-kubernetes-with-agent-sandbox/)（CRD，一个沙箱一个 Pod）；Cloudflare Durable Objects（休眠时零算力）；Modal、E2B、Daytona、[Fly Sprites](https://docs.fly.io/sprites)（快起、可暂停的 microVM 沙箱）；[AWS AgentCore Runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-sessions.html)（每会话一个 microVM，最长 8 小时，11-12 出了[新一代](https://aws.amazon.com/blogs/machine-learning/run-agents-securely-and-efficiently-with-the-next-generation-agentcore-runtime/)）；Google [Agent Compute Engine](https://cloud.google.com/blog/topics/ai-infrastructure/introducing-agent-compute-engine-and-expanded-agent-governance/)（10-22 发布，预览）；[Temporal](https://temporal.io/blog/ai-framework-integrations)（持久化的是编排进度，不保存进程内存）。
- **钱在往这里流**：Daytona 10-20 完成 B 轮 6000 万美元、估值 10 亿美元（[TechCrunch](https://techcrunch.com/2026/10/23/agent-cloud-startup-daytona-hits-1b-valuation-backed-by-firstmark-and-a-whos-who-of-angels/)）；Baseten 9-10 收购了沙箱公司 Blaxel（[The Next Web](https://thenextweb.com/news/baseten-acquires-blaxel-ai-agent-sandboxes)）。

**我的看法：更准的切法是四层**

1. 隔离单元：gVisor、Firecracker、microVM。
2. 控制面：K8s 调度器管机器，专用控制面管高频的挂起和恢复。
3. 计费与占用：按实际 CPU 计费、空闲零占用，对比按预留计费。
4. 状态：整机快照（Substrate、E2B）对比重放进度（Temporal、Workflow），两者互补。

放回这四层看：Fluid 只在第三层，而且面向短请求，长时有状态的 agent 还要另配 Sandbox 和 Workflow；Substrate 横跨第一、二、四层。

「agent 要替代 K8s」这个说法不准。推上有人总结得好：K8s 是为常驻 Pod 设计的，而 agent 九成多的时间在等模型、等工具、等人审批，集群却在为空闲付钱。要替代的是「一个 agent 占一个常驻 Pod」这种用法，K8s 本身还在下面。

Google 和 Anthropic 在同一周走到了同一个形态：Google 11-10 放出 Gemini 自托管环境，Anthropic 11-12 开放自托管 Managed Agents 私测（见第三节）。编排留在模型厂商，执行放进客户自己的环境。中间缺的那一层，Gemini 的文档自己点了名，要客户来补：谁能调用，能用哪个环境，出站放行什么，每次跑了什么。这正是第一节说的「企业里的那一层」。

**留几个问题**

- 做自托管企业平台的，agent 运行时该站在哪一层？自己写，用 Substrate 这类开源件，还是让客户自带？
- 客户到底要多强的隔离？容器够不够，要不要 microVM？能容忍多久的恢复延迟？状态丢一次能不能接受？谁来运维？

## 三、Long-horizon agent：to B 比 to C 更需要

**事实**

- Anthropic 11-13 发了《[Building always-on agents](https://claude.com/resources/articles/building-always-on-agents)》：常驻 agent 并不是一直开着，多数时间在休眠，被事件唤醒后跑一轮。它给了五个基本件：**事件收件箱、定时器、记忆、权限、发件箱**。收件箱用持久化的表，每个用户一个活跃 worker，崩溃可重试；记忆只存查不到的东西；凭据由沙箱外的代理注入；敏感操作挂起，等人回复再继续。
- 同一系列还有：11-06《[The components of agent memory](https://www.anthropic.com/research/components-of-agent-memory)》（记忆分层、离线整理）；10-08 定时 agent 自动化的[参考实现](https://claude.dev/blog/building-effective-agent-automations/)（凭据放保险库，单次花费有上限）；11-12 自托管 Managed Agents 开始[私测](https://claude.com/resources/articles/self-hosted-claude-managed-agents)。
- 别家：Claude Code 的[云端会话](https://code.claude.com/docs/en/claude-code-on-the-web)关了电脑还在跑，可以按日程和事件触发；[Codex Cloud](https://help.openai.com/en/articles/20001545-using-codex-cloud) 同类；[Manus 2.0](https://help.manus.im/en/articles/17190150-what-is-new-in-manus-2-0)（10-01）主打全天在线的云电脑；Google Jules 10-29 宣布年底停服、[并入 Antigravity](https://jules.google/docs/changelog/2026-10-29/)。
- [METR 的任务时长曲线](https://metr.org/time-horizons/) 9-08 起不再更新，最新一个点是 Mythos Preview 早期版，至少 16 小时（区间 8.5 到 55 小时，很宽，超过 16 小时的测量不可靠）。注意它衡量的是「人做这件事要多久」，不是 agent 能连续跑多久。

**我的看法**

- 那五个基本件，放到企业里每一件都更重：收件箱接的是工单、审批、告警；定时器是排班和 SLA；权限要接企业身份和审批流；发件箱要过合规。企业还多要两样：**额度与成本的账**，和**每次运行的完整记录**（审计）。
- 所以 personal agent 的红海，对做企业平台的人是好事。它在替整个行业教育「agent 可以常驻」，而企业要的那几样，恰好是企业平台的本行。

## 四、两个开源样本：LayerFS（存储层）和 Magpie（开发范式）

**LayerFS**（[仓库](https://github.com/Ephemeral-AI-Lab/layerfs)，MIT，11 月中旬约 2800 star，10-21 发 1.0）

- 是什么：给编码 agent 用的文件系统。每个 agent 挂一个完整可写的工作区，底下共享一份已提交的历史；每次工具调用的改动记成一次提交，内容按块去重。工作区连依赖和构建产物一起带着，新开一个不用重装、重编。
- 自报数据：小文件历史上比 Btrfs＋zstd 省约 20 倍空间；在 Magpie 插件的测试里，多开一个并行 agent 约 1 毫秒、复制 0 字节，18 个检查点去重 18.7 倍。
- 我的看法：它甚至能把 Rust 开发者从存储困境里救出来。Rust 项目的 `target/` 构建目录动辄几十 GB，多个 agent 并行时，每个工作副本各编一份，磁盘先爆。LayerFS 让这些副本共享内容，这正是它最能省的地方。这一点我还没有自己实测。
- 局限（1.0）：存储只在 Linux 上验证过，macOS 没测；1.0 时还没有防崩溃的历史；Magpie 插件这条路径读不了二进制文件（上游 [issue #417](https://github.com/Ephemeral-AI-Lab/layerfs/issues/417)），而 Rust 的构建产物正是二进制，这部分要走原生挂载才省得到。

**Magpie**（[仓库](https://github.com/yetone/magpie)，MIT，Go，9-23 建仓，11 月中旬约 3.7 万 star）

- 作为成品：一个本地网关，让各家编码 agent 用任意模型，比如 Claude Code 跑 Kimi、Codex 跑 DeepSeek。它的 Library 把 MCP、skills、hooks、子 agent 写一次，再按各家的格式写进每个 agent，卸载时只删它自己写的东西。支持的 agent 里也包括 WorkBuddy。它对 agent 友好，适合统一管理 MCP 和 skills。
- 作为开发范式（这是我更看重的）：
  - 仓里的 `LESSONS.md` 自述：代码由 agent 写、审、合、发布。每晚复盘当天的提交，把「哪里又修了一次、哪些不该合、哪些验得太薄」写成教训；同一条教训在三个不同的日子出现，就升格进编码规范。
  - 速度：11-15 一天内发了 30 个版本（v0.1.4251 到 4280）；建仓 53 天，版本号已过 4280。我 11-15 取了最近 86 个已关闭的 issue 粗算，从提出到关闭的中位数约 30 小时。
  - 代价也写得很坦白：10-05 那天 220 个提交、约 170 次发布，其中约 40 次是在修当天或前一天刚发出去的东西。
- 我的看法：它就是「long-horizon agent／托管 agent 做开发」的实物。用户在 issue 里许愿，agent 一两天内（中位数）就把功能和修复做完、发出去，比常见的企业排期快得多。速度快，返工也多，靠每晚复盘把返工收成规矩。它是开源项目，整个过程 build in public，谁都能看。值得参考的是这套开发范式（许愿入口、agent 全流程、夜间复盘升格规范），不只是这个工具。它的关闭时间也有长尾，四分之一超过 10 天，「快」主要快在中位数上。
- 边界：说实话，Magpie 有点灰色地带。它的订阅桥接和多账号轮换，在服务条款上有争议，企业不能照搬这部分用法。值得学的是它的开发方式，和它管理 MCP、skills 的方式。

**留个问题**：「许愿 → agent 做 → 夜间复盘」这种节奏放进企业软件，哪些环节能照搬，哪些会被 SLA、合规和客户验收卡住？

## 五、Poppy：个人 agent 进企业的入口标准

**事实**

- Poppy 即 Personal Agent Protocol，Sierra 牵头、Meta 等参与（[发布文](https://sierra.ai/blog/releasing-poppy)）。企业在 `/.well-known/poppy.json` 里声明能被 agent 调用的接口和登录方式，个人 agent 通过 OAuth 拿授权；它建在 MCP、OpenAPI 之上。10-09 出草案，**11-13 发 1.0**；Shopify 全部商户默认开启，Meta 的个人 agent 访问网站时会先找 Poppy，设计伙伴超过 100 家。
- 它影响大，主要因为接入的平台多。
- 也有反方向的：有二手报道说 United 限制第三方 agent 订票（[来源](https://aiagentstore.ai/ai-agent-news/this-week)）。不是每家企业都愿意开门。

**我的看法**

- 另一半问题浮上来了：不光是「agent 怎么跑」，还有「企业怎么被 agent 安全地访问」。企业要有一层：声明能力、做授权、留记录。
- 中国的生态更封闭，可能是各大厂系各出一套。
- 对企业平台来说，end-user OAuth 这类能力是刚需，企业客户的需求很强。落到具体场景，比如教育：学生、老师每人都是独立用户，要各自授权、各自留记录。谁无视这类需求，谁就是拿客户当傻子，要么就是在闭门造车、自娱自乐。
- to B 不只是卖给「企业」，企业里面还有无数个 individual。to B 和 to C 的界限本来就不清。不能拿「这属于 to C」当理由给自己设限，否则在客户满意度、在客户成功和交付价值上，必定会失败。
- 避开红海，不等于一味避战。要辩证地看，有战略地看：战略上看清哪里是红海，战术上该接的需求照接；战略和战术分开，low ego 地去对待、去设计、去落地。做 to B 的团队最容易犯的病就是 ego 太大，这一条我也在提醒自己。
- 再看几个大公司怎么做事：
  - 英伟达和台积电做了几百亿美元的生意，黄仁勋公开说过两家之间没有正式合同，靠的是信任和交付（[来源](https://econotimes.com/Nvidia-Chose-TSMC-in-1996-for-Trust-Beyond-Manufacturing-Terms-1756100)）。上下游很多供应商也是这样，并没有签到尽善尽美。
  - 据报道，xAI 在孟菲斯的数据中心，许可没批全就先用燃气轮机发电，招来居民投诉，后来拆了一部分（[Inside Climate News](https://insideclimatenews.org/news/17072025/elon-musk-xai-data-center-gas-turbines-memphis/)）。这个例子两面都能讲：快有快的代价，周边的人也是要顾的。
  - Anthropic 这个月被报道买了约 34 亿美元的燃气发电设备（约 1.7 GW）（[TechCrunch](https://techcrunch.com/2026/11/09/anthropic-joins-ais-natural-gas-frenzy-buys-3-4b-worth-of-turbines/)）；它递交的上市招股书写明，新建数据中心靠现场燃气发电，燃料成本转嫁、没有上限（[Fortune](https://fortune.com/2026/11/10/anthropic-3-4-billion-deal-gas-data-centers-ai-ipo/)）。
  - 这些公司都没有等一切尽善尽美才动手。万亿市值的英伟达尚且如此，我们为什么要作茧自缚？哪些约束是客户真要的，哪些是自己给自己加的，值得分清楚。

**留个问题**：企业的应用和工作流，要不要能被外部的个人 agent 按这类标准调用？如果要，end-user OAuth、鉴权和审计放在哪一层？

## 六、跟桌面 agent 协作，不竞争

**事实：它们都在开门**

- Codex：插件里能带 skills 和 MCP，可以加 GitHub 上的插件市场源（[文档](https://learn.chatgpt.com/docs/plugins)）。
- Claude Code：插件、skills、连接器 11-09 起并到一个 Plugins 页（[说明](https://support.claude.com/en/articles/17740565-manage-plugins-skills-and-connectors-from-one-plugins-page)）。
- 腾讯 WorkBuddy：10-29 宣布开放架构，可接企业自研和第三方 agent，也能接第三方 IM，用 MCP 接 ERP、CRM（[报道](https://finance.sina.com.cn/stock/t/2026-10-29/doc-iniwwiey2867305.shtml)）；托管智能体可经 API、A2A 调用（[报道](https://www.stdaily.com/web/gdxw/2026-10/30/content_605760.html)）。
- 字节：豆包工作（8-25）支持自定义 MCP 和技能（[文档](https://www.doubao.com/work/docs/zh-cn/articles/705018132598-plugins)）；扣子的文档称可以托管 Claude Code、Codex CLI（[文档](https://docs.coze.cn/cozespace_agent_overview)）；扣子企业版 11-30 起停止新售（[IT 之家](https://www.ithome.com/1/022/432.htm)）。
- 标准层：Agent Skills 10-22 捐给 Linux 基金会下的 AAIF，自称超过 70 个平台集成（[Anthropic](https://www.anthropic.com/news/donating-agent-skills-to-the-agentic-ai-foundation)）；A2A 8 月也进了 AAIF。

**我的看法**

- 「协作」在技术上可行：MCP 和 skills 是现成的接入格式。从接入方的角度看，卡点更多在各家的上架审核和开放节奏，不在技术。
- 定位可以说成：桌面 agent 是员工的入口，企业平台是企业里的那一层（运行、权限、记录、SOP）。
- 我一直的主张：**每一个支持 n8n 或 Zapier 连接器的地方，都应该有我们的身影**，包括但不限于 ChatGPT 网页版、Manus 等。n8n 和 Zapier 已经替我们探过路，知道哪些平台肯接第三方自动化，它们的连接器清单就是一张现成的地图。

**顺手查的公开情况（11-16，只看公开页，没有实测）**

| 平台 | 和 Zapier | 和 n8n |
|---|---|---|
| ChatGPT（含网页版） | 网页客户端有接 Zapier MCP 的[教程](https://zapier.com/apps/ai-tools/chatgpt) | 可以连 n8n 的 [MCP](https://blog.n8n.io/n8n-mcp-server/) |

Dify 在 Zapier 上的 4 个动作是聊天、上传文件、建议问题、消息反馈。对照同类，Langflow 在 Zapier 上有「Run Flow」，Manus 有任务创建和任务状态触发器，Dify 在 Zapier 上的接口覆盖还可以更全。

## 七、可信度可以靠公开的行为来证明

**事实**

- 黄仁勋 11-12 辞去英伟达 CEO，董事会在内外部找继任者。网上出现了请愿他回归的网站，签名过了 10 万。我看下来，这个网站没有 KYC，没有任何正式的东西，一堆人就这么签了，理论上你可以冒名替别人签。但马斯克 11-14 发帖说他也签了（[Yahoo Finance](https://finance.yahoo.com/markets/stocks/articles/elon-musk-joins-100-000-172500045.html)），那他签的字就千真万确。

**我的看法**

- 可信度可以靠公开的行为来证明，不一定要靠流程。
- 换成很多组织，同样一件事要走 OA、审批、会签。等手续走完，一切都凉了，再来一句这事可以，或者有待商榷、需要互相让步。
- 速度是创业公司最后的优势。可以列一张清单：哪些事可以先做、后补手续。

## 最后：企业里那一层不是空地

提到 n8n，就想起 LangChain。

**事实**

- LangChain 11-13 宣布完成 C 轮：3 亿美元，估值 30 亿美元，CapitalG（Alphabet 旗下的成长基金）领投。估值是 2025 年 10 月 B 轮（12.5 亿美元）的 2.4 倍，累计公开融资约 4.6 亿美元（[TechCrunch](https://techcrunch.com/2026/11/13/ai-agent-startup-langchain-hits-3b-valuation/)）。钱主要投 LangSmith（构建、部署、监控、治理 agent），对外的说法是做企业 agent 的「中立之家」，自称 7000 多家组织在用；收入未披露（[CityBiz](https://www.citybiz.co/article/933425/langchain-raises-300-million-series-c-led-by-capitalg-at-3-billion-valuation/)）。

**我的看法**

- 它要占的，正是第三、六节说的「企业里那一层」：部署、监控、治理。这一层不是空地，资本已经押了一家。讲「协作而非竞争」的时候，要能说清和 LangSmith 的差别。

对了，按公开报道的数字算，对方的估值已经比我们现在大一个数量级。
